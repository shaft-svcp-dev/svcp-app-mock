# 人間に読みやすいコードを書く

## 基本方針

コードは実行結果だけでなく、次に読む人が意図を正確に理解できることを重視する。既存のプロジェクト規約を優先し、必要な動作を保った最小限の実装にする。コードだけでは分からない判断や制約がある場合は、コメントを適切に書く。後回しにしない。

## 実装手順

1. 対象コード、周辺コード、プロジェクト規約、既存テストを確認する。
2. 要件や期待する動作が不明な場合は、推測で実装せず質問する。
3. 実装前に失敗するテストを追加し、期待する動作を明確にする。
4. 次の可読性基準に従って、テストを通す最小限のコードを書く。
5. コメントを適切に書く。コードだけでは分からない判断・制約・非自明な変換を対象の直上に残し、言い換えだけのコメントは書かない。既存コメントが実装と一致しなければ更新または削除する。
6. テスト、型検査、Lintを実行する。

## 可読性基準

- 役割と意図が伝わる具体的な名前を使う。
- 一つの関数、クラス、モジュールには一つの明確な責務を持たせる。
- 早期リターンなどを使い、条件分岐とネストを追いやすくする。
- データの生成元、変換、利用先を追跡しやすい構造にする。
- 重複を減らすが、一度しか使わない処理を理由なく抽象化しない。
- 短さより理解しやすさを優先し、過度な省略や技巧的な記述を避ける。
- エラー条件と境界値を明示的に扱う。
- 周辺コードの言語、命名、構成、フォーマットに合わせる。
- ダミーデータを実装に追加しない。

## コメントの基準

コメントは量ではなく、コードだけでは分からない情報を伝えるために使う。書くときは「何をしているか」ではなく「なぜそうしているか」を残す。

### 書く場所と書き方

- 説明する対象の直上に置く。離れた位置やファイル末尾にまとめない。
- 言語と形式は周辺コードに合わせる。このリポジトリの実装コメントは日本語にする。
- 1つの判断につき必要な文だけ書く。前置きや装飾は付けない。
- 名前を直せば済むなら、コメントではなく名前を直す。

### 次の場合はコメントを書く

- 業務上または技術上の判断理由がある。
- 一見不要に見える処理に、互換性や安全性などの制約がある。
- アルゴリズム、正規表現、境界条件、非自明な変換や不変条件の説明が必要である。
- 公開APIの契約、前提条件、副作用、例外をプロジェクト規約に従って説明する必要がある。
- セキュリティ上重要な検証について、守るべき条件を示す必要がある。
- 仕様上できないこと、意図的に実装していない理由がある。

### 次のコメントは書かない

- コードを日本語や英語に言い換えただけのコメント。
- 名前を明確にすれば不要になるコメント。
- 実装と同期できない将来予定や推測。
- 変更履歴や作業者向けの一時的なメモ。

既存コメントが実装と一致しない場合は、必ず更新または削除する。

### 例

適切:

```ts
// デザインは「アップロード日時」の降順表示のみ。他の並び替えキーは仕様にない。
```

```ts
// Figma の表示形式 `YYYY/MM/DD HH:mm` を Date.parse できるハイフン区切りにする
return Date.parse(value.replaceAll('/', '-'))
```

不適切:

```ts
// クエリで絞り込む
const visibleVideos = computed(() => { /* ... */ })
```

## 完了条件

- 初見の開発者が処理の目的と流れを追える。
- コードだけでは分からない判断・制約に、適切なコメントが書いてある。
- コメントが「何をしているか」ではなく、必要な「なぜ」を補足している。
- 言い換えだけのコメントや、実装と食い違うコメントが残っていない。
- 外部仕様と既存の必要な動作を壊していない。
- 追加・変更した動作がテストで保護されている。
- 関連する検証がすべて成功している。
